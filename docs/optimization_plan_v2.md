# Capsule Transfer 优化与改进计划书 (V2 - 务实与工程边界版)

本项目是一个服务于 Reaper 用户的局域网点对点音频工程/素材分发工具。基于对核心传输逻辑、DAW 导出链（Lua 脚本）以及系统架构的深度求证，本项目当前的优化重点应放在**提升大文件传输的鲁棒性**、**保障数据一致性与安全性（防止工程损坏与素材覆盖）**、**引入自动化测试**以及**基于真实反馈的渐进式演进**上。

本计划书摒弃了盲目引入复杂协议或重写核心的设想，转而专注于解决实际协作中高概率发生的边界隐患。

---

## 核心设计目标

1. **零数据污染 (Data Integrity)**：确保大文件在传输中断、断电、磁盘满等极端状况下，绝不损坏已有胶囊库。
2. **零内存崩溃 (Low Memory Footprint)**：消除 Lua 侧与 Python 侧因大音频文件拷贝导致的虚拟机/进程内存溢出 (OOM) 隐患。
3. **消除素材冲突 (No Asset Collision)**：解决多音轨引用不同目录下同名素材在打包时发生静默覆盖的恶性 Bug。
4. **渐进式解耦 (Progressive Refactoring)**：在自动化测试护航下，对前后端代码进行小步慢跑的模块化拆分。

## 阶段一：测试先行与接收端事务性保护（高优先级）

此阶段专注于系统安全性的“防线建设”，在大文件并发与接收事务性上做到绝对可靠。

### 1. 建立核心功能单元测试
在没有测试覆盖的情况下重构高度耦合的后端是极具风险的。首要任务是为以下模块编写 Python 单元测试：
* **`server/bundle.py`**：测试 ZIP 安全打包、哈希校验，及解包路径解析。
* **加密与签名**：测试身份公钥生成、签名校验边界。
* **路径验证**：防御恶意路径穿越（防范 Zip Slip 漏洞）。
* **插件相似度比对**：为 `_plugin_available` 匹配逻辑编写测试用例。

### 2. 实现流式接收的“原子提交” (Atomic Commit)
* **现状**：目前接收大文件解压直接写入正式的 `CAPSULES_DIR`。如果在写入一半时断开或出错，会留下损坏的半成品目录，污染本地库。
* **改进方案**：
  1. 引入临时缓存目录（如 `.tmp`）。
  2. `/api/p2p/import` 在接收 ZIP 包并解压时，全程写入 `.tmp/temp_uuid/`。
  3. 解压完成后，读取其 `manifest.json`，校验包体 SHA256 与发送方是否匹配。
  4. 只有当**完整性校验 100% 通过**后，才调用系统级原子移动（如 `shutil.move`）将其移动至正式库目录 `CAPSULES_DIR/uuid/` 并完成数据库写入。
  5. 传输失败或超时后，后台定时清理 `.tmp` 下的残留未完成文件夹。

### 3. ZIP 安全防护与物理边界处理
* **防御 Zip Slip**：在解包时，严格检查压缩包内所有文件的相对路径。一旦发现包含 `../` 或绝对路径尝试写入胶囊库之外的敏感区域，立即终止并清除。
* **磁盘空间预检**：在 P2P 握手握手请求中，接收方获取胶囊的大小。检查本地可用磁盘配额，若磁盘余量不足，直接返回 `HTTP 400 (磁盘空间不足)` 以阻止无效传输。
* **冲突恢复设计**：细化 UUID 冲突时的覆盖与备份机制。重命名时若发生异常，需要有 Rollback（回滚）逻辑。

## 阶段二：大文件流式 IO 与 Lua 捕获边界修正（中优先级）

此阶段解决大工程文件读写时的性能隐患，并修补 Lua 导出端的边界缺陷。

### 1. 流式打包、发送与接收 (Python 侧)
* **优化内容**：
  * 重构 `build_bundle` 移除大字节数组在内存中的滞留。ZIP 压缩直接流式输出至磁盘文件。
  * 后端发送和接收均改用 Chunked 传输。在 Flask/requests 发送时通过缓冲区循环读取文件块；在接收时也避免用 `f.read()` 全量加载。
  * **进度实时化**：在流式读写的 Chunk-level 传输循环中，将当前已传输字节数、总字节数以及传输速率计算出来，通过 SSE (`/api/events`) 实时推送到前端。

### 2. 修复 Lua 捕获端的内存与同名素材覆盖冲突
* **解决 Lua OOM 崩溃**：
  在 `main_export2_windows.lua` 的 `CopyFile` 中，弃用一次性读入字符串的 `srcFile:read("*a")`，改用 **Buffer 分块读写模式**：
  ```lua
  local chunk_size = 65536 -- 64KB
  while true do
      local block = srcFile:read(chunk_size)
      if not block then break end
      dstFile:write(block)
  end
  ```
* **解决同名素材覆盖**：
  * **现状**：收集选中 Item 的音频文件时，`kick.wav`（源目录 A）和 `kick.wav`（源目录 B）在打包进胶囊的 `Audio/` 文件夹时会发生覆盖。
  * **改进方案**：在收集活动媒体时，如果遇到同名文件，不应直接以 basename 存储，需对其绝对路径计算短哈希（如 MD5 前 6 位）作为文件名后缀（如 `kick_ab12cd.wav`），并在 RPP 中同步更新引用路径，确保素材绝不混淆。

### 3. 插件匹配与误报机制细化
* **内置插件过滤**：维护一个标准 Cockos 内置插件清单，默认将其标为安全可用。
* **macOS 平台 AU 插件扫描**：在 macOS 节点上增加对 `reaper-auplugins.ini` 的解析，提取本地已安装的 AU 插件。
* **定义“比对 vs 忽略”边界**：对于部分跨平台但因命名差异被标记为“缺失”的常见插件，建立别名转换和忽略规则。

## 阶段三：网络发现与代码渐进式拆分（中低优先级）

在底座与性能边界处理妥当后，优化局域网用户体验并对代码结构进行低风险的重构。

### 1. 混合型局域网服务发现 (mDNS + 手动后备)
* **策略**：引入 **mDNS/Bonjour** 作为发现协议，在局域网内广播本机服务，减少对大量 IP 并发端口扫描的行为。
* **边界处理**：多播和广播在许多录音棚、校园网或企业 VLAN 之间是默认被交换机阻断的。因此，**mDNS 仅作为快速感知的辅助手段**，系统必须无缝保留现有的手动填写 IP 地址、扫描 `/24` 子网以及已保存联系人列表作为坚固的后备通路。

### 2. 渐进式后端重构 (Progressive Backend Decoupling)
* **策略**：反对一次性全面迁移到 Flask 蓝图。
* **实施方案**：
  1. 优先将 `app.py` 中臃肿的业务逻辑（如本地胶囊的 SQLite CRUD 操作、ZIP 包读写管理）解耦抽离到独立的纯 Python Service 模块（如 `services/db_service.py` 和 `services/capsule_service.py`）中。
  2. 针对这些抽离出的 Service 补充单元测试。
  3. 当 Service 稳定且测试通过后，再将 `/api/capsules/*` 和 `/api/p2p/*` 等路由逐步重构为 Flask 蓝图，将 `app.py` 的职责收缩为纯粹的入口配置。

### 3. 渐进式前端重构 (Progressive Frontend Modularization)
* **策略**：不盲目引入全局状态库（如 Zustand）。当前应用的 Props 传递层级浅，没有明显的深层传递链，引入第三方状态库只会徒增复杂度与包体大小。
* **实施方案**：
  1. 保持当前由单层 App 传 Props 的结构。
  2. 将 125KB 的 `App.jsx` 仅做文件级的拆分，把嵌套在内部的 `LibraryView`、`TransferView`、`ContactsView` 等组件抽离到独立的 `.jsx` 文件中。
  3. 将 API 交互逻辑与网络轮询操作封装为 React 自定义 Hooks（如 `usePeerDiscovery`、`useTransfers`），实现表现层与逻辑层的分离。

## 阶段四：数据驱动的远期探索（低优先级）

以下功能应根据阶段一、二上线后，收集的实际用户反馈和日志数据进行理性评估，切忌方案先行。

1. **协议级断点续传**：只有在真实日志中观测到高频的“网络不稳定导致大文件传输中断率高”的数据支撑时，才考虑设计传输控制协议（涉及传输状态 ID、临时分块清单、清理过期挂起文件的机制）。
2. **传输加密 (TLS/HTTPS)**：如用户在弱网/公共局域网有强烈的隐私保密需求，再行设计自签证书机制。这需要严密论证首次信任（TOFU）的证书绑定机制、以及移动设备 IP 变动时的证书轮换方案，防范自签证书被浏览器安全策略拦截。
3. **Tauri 原生 Rust 化**：保留纯 Rust 重写核心作为长期的愿景储备。不应在近期浪费开发精力去承担双系统下重写压缩解压、网络协议、文件读写的庞大回归风险。
